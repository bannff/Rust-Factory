# Canonical Brick Standard

Define the Rust-native taxonomy and scaffold contract for the full Rust Factory portfolio before creating or refactoring further brick families. This standard is a reusable architecture contract, not a generic runtime or a line-for-line port of Python Factory/Polylith.

1. Every portfolio item SHALL be classified as exactly one of: a capability family, adapter infrastructure, composition base, or optional domain pack. Only a capability family may own a `<brick>`; shared infrastructure such as `mcp-transport` is an adapter, and MCP/API/worker/edge processes are composition-base binaries, never cores. The capability roadmap and approved mature shape SHALL be recorded in a GitHub issue and tracked in GitHub Projects.
2. A capability family SHALL have its own GitHub issue and GitHub Projects roadmap entry before any package is created; that tracking SHALL identify the family and its intended owning crate. A family SHALL NOT receive a package until the flagship autonomous loop or another demonstrated consumer drives it; a deferred family remains roadmap-only and its named crate does not exist on disk. Creating a package earlier would freeze a contract that no consumer has shaped. A live provisional port with exactly one demonstrated direct consumer MAY be extracted into its canonical capability package only when the tracking issue records an explicit product mandate, the Rust SME approves the replacement contract before setup, and implementation performs one atomic one-way migration that removes the provisional port without aliases, facades, or a second authoritative path. Issue #34 is the precedent for this narrow extraction rule. It does not permit a zero-consumer package or a package for a newly invented contract. Storage is the sole explicit zero-consumer exception: it MAY receive a real capability package before a code consumer because issue #28 records both a direct product mandate and an independently gated bounded object-storage contract. This exception does not weaken the general consumer-first rule, and migrations from Agent or Evaluation remain separately gated work. When a tracked family is committed but not yet designed, it MAY use the status-only core package tree from requirement 10 as a narrow, explicitly bounded intermediate step: it contains only compile-safe status documentation and private placeholder modules/tests, has zero non-stdlib dependencies, exposes no public semantic API, and claims no behavior or guarantees. It SHALL be replaced by a specified or implemented core contract before any adapter role is instantiated.
3. A specified or implemented `<brick>` is permitted only when the family owns stable typed models, deterministic rules, error taxonomy, and at least one consumed effect port. It is a library and owns versioned models/commands/results/events, validated newtypes, semantic validation, public-safe error categories, state invariants, and consumed port traits. It SHALL NOT depend on adapters, transports, `rmcp`, Tokio runtime/I/O, provider/storage/network/filesystem frameworks, or concrete adapter types.
4. Every Cargo package in the workspace SHALL declare an authoritative machine-readable record in `[package.metadata.rust-factory]` containing exactly three fields: `family`, closed `role` (`brick` for a capability crate with its feature-gated adapter modules, `core` for a status-only family with no behavior yet, `infrastructure` for a shared package owning no capability, and `server`, `mesh`, or `test-support` for the three a brick cannot contain), and closed `status` (`scaffolded`, `specified`, `implemented`, `migration-pending`, or `deprecated`). No further metadata field is permitted, so a guarantee SHALL be stated in crate documentation and proven by tests rather than asserted in manifest data. `family` SHALL name the family tracked by the package's GitHub issue and GitHub Projects roadmap entry, and the package name SHALL match its directory and belong to its declared family. Crate-level documentation SHALL mirror this data for human readers. Status is not a public Rust API and is never inferred from version or dependencies. Of the five statuses only `scaffolded` currently carries an enforced structural obligation (requirement 10); `specified`, `implemented`, `migration-pending`, and `deprecated` are declarations of intent and SHALL NOT be read as a guarantee. Deterministic workspace package/brick structure validation SHALL cover every package and SHALL enforce workspace inventory, package placement and targets, exactly-three-field metadata, status-only family structure, adapter isolation, and Makefile quality-matrix coverage. A status-only family's packages SHALL declare only `scaffolded`, and `role = "core"` SHALL be paired only with `status = "scaffolded"` so a package cannot exempt itself from brick enforcement rules. Roadmap registration remains a GitHub workflow prerequisite rather than an in-repository bidirectional registry.
5. A mature `role = "brick"` package SHALL own a mandatory bounded, transport-agnostic, feature-gated `mcp` handler. The handler SHALL implement the shared `HandlerContribution` contract and expose generated `<namespace>_capabilities` and `<namespace>_schema` tools. Its namespace SHALL match `[a-z][a-z0-9_]{0,63}`; crate hyphens normalize to underscores. The two discovery tools SHALL remain available even when the brick's only safe MCP surface is introspection. Sensitive bricks, including Policy, Auth, Storage, Knowledge, and LLM Gateway, SHALL prohibit privilege and raw-bypass operations such as caller-supplied authorization decisions, grant mutation, token minting, raw object CRUD, unrestricted corpus access, and unrestricted provider invocation.

   Other adapter modules retain explicit eligibility rules: `memory` or `local` only after a core-owned stateful port and truthful process-local semantics exist; `fs` or a vendor module only to implement an existing core port; and `settings` only after a bounded declarative selection surface is specified. A vendor module SHALL be named for its vendor crate. `settings` owns configuration shape, not its source or adapter-selection match, which belong to the project binary. Adapter modules SHALL be feature-gated even when they add no dependency. No feature is enabled by default, so a brick's default build resolves no adapter dependency; Cargo feature unification means this is a source/dependency-resolution guarantee, not a framework-free artifact claim.

   In-process brick-to-brick calls SHALL use consumed port traits directly and SHALL NOT round-trip through MCP. Packages under `crates/` are libraries and SHALL declare no binary target. Only three roles may be separate packages because a brick cannot contain them: `server` under `projects/`, `mesh`, and `test-support`. Shared infrastructure such as `mcp-transport` uses `role = "infrastructure"` and owns no capability. No generic core, prelude, utility, validation umbrella, dynamic adapter registry, or plugin-discovery crate may be introduced.
6. Every project SHALL contain exactly one binary target, launch exactly one process, and expose exactly one unified MCP server/router over `BoundedStdioTransport`. Its `role = "server"` composition root SHALL statically combine the selected bricks' `HandlerContribution`s and separately typed `factory_*` project meta-tools. It SHALL NOT launch per-brick servers or discover handlers dynamically. It owns runtime lifecycle, transport binding, configuration sources, host-derived trusted context, Policy construction, concrete adapter selection/injection, aggregate ingress/egress and discovery ceilings, duplicate-name rejection, logging, admission/cancellation, and orderly shutdown. Brick `mcp` modules expose handler construction only; they SHALL NOT read stdin, write stdout, construct `BoundedStdioTransport`, call `serve_stdio`, or choose a runtime.

   Brick tools SHALL use `<namespace>_<operation>`; project meta-tools exclusively use `factory_<operation>`. Construction SHALL fail closed on invalid or duplicate namespaces/tool names and aggregate schema/discovery budget violations. A project composition root owns no capability.
7. Each external operation SHALL follow this sequence: (a) bounded transport framing; (b) strict boundary DTO deserialization and generated discovery schema; (c) private DTO-to-core conversion and newtype construction; (d) authoritative semantic/cross-field validation and stable error classification; (e) host-derived trusted context plus exact Policy authorization immediately before every non-introspection effect or tenant-scoped read; (f) one injected effect with explicit idempotency, deadline/cancellation, and evidence rules when consequential; and (g) allowlisted bounded response projection before transport write. Caller input SHALL NOT establish identity, Policy decisions, grants, ceilings, trusted paths, or authorization context. Introspection tools MAY omit authorization only when they are bounded and disclose no grants, tokens, paths, tenant data, corpus/provider content, or backend secrets.
8. The Rust-native Pydantic-equivalent SHALL remain layered: exact-pinned `serde` derives and `schemars` schemas at transport/config DTO boundaries, Rust enums and fallible newtype constructors for structural validity, and explicit core validation for semantic/cross-field/state/policy invariants. Deserialization/schema success SHALL NOT be considered domain validation or authorization. No `validator`, `garde`, ORM validation layer, or runtime-schema validator is added without a separate concrete adapter-bound gap and dependency decision.
9. All external object DTOs SHALL use closed serde schemas (`deny_unknown_fields` unless an explicitly documented extension map is required), deliberate enum tagging/renaming, raw and semantic ceilings, and private conversion. External responses SHALL use separate safe projections and omit internal causes, secrets, paths, trusted context, and raw Policy artifacts unless a specification explicitly authorizes an evidence projection. Before every write, `BoundedStdioTransport` SHALL serialize and measure the complete `TxJsonRpcMessage`, including the caller-controlled JSON-RPC request ID, against the 64 KiB ceiling. It SHALL fail closed without a partial write when over limit. Smaller handler-result limits are required headroom, not proof that the complete envelope fits.
10. Mandatory status-only `<brick>` package trees are `Cargo.toml`, `src/lib.rs`, `src/model.rs`, `src/validation.rs`, `src/error.rs`, `src/port.rs`, `src/service.rs`, and `tests/public_contract.rs`. Each placeholder identifies metadata status, contains documentation/comments only, and compiles with no dependencies or exported semantic API. Once a family becomes a mature `role = "brick"`, it SHALL add the mandatory feature-gated MCP handler and conformance tests. The stable module vocabulary is `lib`, `model`, `validation`, `error`, `port`, `service`, `mcp`, `memory`, `local`, `fs`, vendor, and `settings`; a path predicts its concern. A `role = "server"` project uses `src/{main.rs,config.rs,composition.rs}` and tests covering unified routing, duplicate startup rejection, authorization, and bounded stdio behavior.
11. Existing mature bricks that lack the mandatory handler, discovery tools, or shared contribution contract are explicit migration debt, not architectural exceptions. A temporary allowlist SHALL name each debt item. Removal SHALL require compiled and runtime `HandlerContribution` conformance, generated `<namespace>_capabilities` and `<namespace>_schema`, exact namespace/tool ownership, and Makefile feature coverage; regex-only source evidence is insufficient. Entries SHALL be removed one brick at a time, and the allowlist SHALL be deleted when migration completes. Documentation SHALL NOT claim all bricks comply before that evidence exists.

   Migration SHALL preserve approved core behavior while moving all process lifecycle into the first unified project server tracked by issues #6, #17, and #39. Agent, Project, Workflow, and Evaluation handler behavior remains bounded during composition; sensitive bricks may migrate first with introspection-only handlers. Shared contracts are otherwise extracted only after demonstrated consumers prove a stable narrow need. Vendor, durable, remote, async, and mesh adapters remain separately specified work.

## Non-goals

No portfolio-wide framework selection; mass import of provider/storage/runtime dependencies; automatic crate generation; change to existing core behavior during standard publication; dynamic plugin discovery; per-brick server processes; remote inter-brick calls through MCP; or claim that all portfolio entries already comply or are production-ready.
