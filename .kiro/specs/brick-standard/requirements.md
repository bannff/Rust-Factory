# Canonical Brick Standard

Define the Rust-native taxonomy and scaffold contract for the full Rust Factory portfolio before creating or refactoring further brick families. This standard is a reusable architecture contract, not a generic runtime or a line-for-line port of Python Factory/Polylith.

1. Every portfolio item SHALL be classified as exactly one of: a capability family, adapter infrastructure, composition base, or optional domain pack. Only a capability family may own a `<brick>`; shared infrastructure such as `mcp-transport` is an adapter, and MCP/API/worker/edge processes are composition-base binaries, never cores. The portfolio table is the family-level registry and states each approved mature shape.
2. A capability family SHALL be recorded in the portfolio registry before it owns any package, and the registry row — naming the family's owning crate — is the designated home for that concern. A family SHALL NOT receive a package until the flagship autonomous loop or another demonstrated consumer drives it; a family with no package is recorded as `Deferred` and its named crate does not exist on disk. Creating a package earlier would freeze a contract that no consumer has shaped. When a family is committed but not yet designed, it MAY use the status-only core package tree from requirement 10 as a narrow, explicitly bounded intermediate step: it contains only compile-safe status documentation and private placeholder modules/tests, has zero non-stdlib dependencies, exposes no public semantic API, and claims no behavior or guarantees. It SHALL be replaced by a specified or implemented core contract before any adapter role is instantiated.
3. A specified or implemented `<brick>` is permitted only when the family owns stable typed models, deterministic rules, error taxonomy, and at least one consumed effect port. It is a library and owns versioned models/commands/results/events, validated newtypes, semantic validation, public-safe error categories, state invariants, and consumed port traits. It SHALL NOT depend on adapters, transports, `rmcp`, Tokio runtime/I/O, provider/storage/network/filesystem frameworks, or concrete adapter types.
4. Every Cargo package in the workspace SHALL declare an authoritative machine-readable record in `[package.metadata.rust-factory]` containing exactly three fields: `family`, closed `role` (`brick` for a capability crate with its feature-gated adapter modules, `core` for a status-only family with no behavior yet, `infrastructure` for a shared package owning no capability, and `server`, `mesh`, or `test-support` for the three a brick cannot contain), and closed `status` (`scaffolded`, `specified`, `implemented`, `migration-pending`, or `deprecated`). No further metadata field is permitted, so a guarantee SHALL be stated in crate documentation and proven by tests rather than asserted in manifest data. `family` SHALL name a family declared in the portfolio registry, whatever the status, and the package name SHALL match its directory and belong to its declared family. Crate-level documentation SHALL mirror this data for human readers. Status is not a public Rust API and is never inferred from version or dependencies. Of the five statuses only `scaffolded` currently carries an enforced structural obligation (requirement 10); `specified`, `implemented`, `migration-pending`, and `deprecated` are declarations of intent and SHALL NOT be read as a guarantee. Deterministic validation SHALL cover every package and SHALL enforce registry agreement in both directions — no package may declare an unregistered family, no capability family in the registry may go undeclared, a status-only family's packages SHALL declare only `scaffolded`, `role = "core"` SHALL be paired only with `status = "scaffolded"` so a package cannot exempt itself from the brick enforcement rules, and a family's registry row SHALL name one of the packages it actually owns — so the workspace, package metadata, and registry cannot drift.
5. Adapter modules have one explicit eligibility rule each: a `memory` module is added only after a concrete core-owned stateful port and truthful process-local semantics exist; an `fs` or vendor module only to implement one existing core port; an `mcp` module only after a bounded authoring/operational surface is specified. Only three roles may be a separate package, because a brick cannot contain them: `role = "server"` for a deployable binary under `projects/`, `role = "mesh"` for a peer-coordination adapter after an approved process-boundary specification, and `role = "test-support"` after two consumers need shared fixtures. Shared cross-family infrastructure such as `mcp-transport` uses `role = "infrastructure"` and owns no capability. A brick uses `role = "brick"`. No generic `factory-core`, prelude, utility, backend, storage, or validation umbrella crate may be introduced.

  A brick is exactly one crate, named for its capability. Its agent-facing MCP surface and every local adapter are feature-gated modules inside that crate — `mcp`, `memory`, `fs` — so one capability is one unit to find, name, compose, and reason about. No feature is enabled by default, so the default build resolves no transport, schema, error-framework, filesystem, or async-runtime dependency and every adapter is opt-in. This is not a claim of zero dependencies: a core may use a focused library such as `sha2`. Adapter code SHALL appear only under its own feature-gated module path, and core modules SHALL name no adapter dependency; deterministic validation enforces this as a path rule, because consolidation removes the crate boundary that previously made it structural. A feature-conditional attribute SHALL NOT appear on a domain type: boundary types belong in the adapter module, per requirements 8 and 9.

  This trades one honest guarantee for reasoning cost. Two mechanisms, two guarantees, and they SHALL NOT be conflated. A path rule over source text keeps an adapter dependency from being named outside its own module. A per-crate dependency-resolution check confirms each brick's default build reaches no adapter dependency. Neither can assert framework-free **artifacts**: Cargo unifies features per build graph, so a binary composing several bricks with `mcp` enabled links one framework-carrying build of each. Documentation SHALL state the guarantee at source level only.

  In-process brick-to-brick calls SHALL use the consumed port trait directly and SHALL NOT round-trip through MCP. A composition binary MAY host several brick MCP surfaces on one transport.

  A brick that decides what agents may do is not itself agent-operable: `policy` SHALL NOT expose an MCP surface, because authorizing through caller input would violate requirement 7's rule that caller inputs never establish trusted identity, decisions, grants, or ceilings.

  Packages under `crates/` are libraries and SHALL declare no binary target. Deployable binaries live under `projects/<name>/`, SHALL declare `role = "server"`, and are the only packages that own a process. Residence under `projects/` and `role = "server"` SHALL agree.
6. A `role = "server"` package under `projects/` SHALL be a binary-only composition root. It owns runtime lifecycle, transport binding, configuration sources, host-derived trusted context, Policy resolver construction, concrete adapter selection/injection, logging initialization, and orderly shutdown. An `mcp` module SHALL expose transport-agnostic service/handler construction only; it SHALL NOT read `stdin`, write `stdout`, call `serve_stdio`, construct `BoundedStdioTransport`, or choose Tokio process lifecycle. Consequently a brick declares no direct `tokio` dependency.
7. Each external operation SHALL follow this bounded sequence: (a) adapter transport framing and byte/item/depth limits; (b) strict boundary DTO deserialization and generated discovery schema; (c) private DTO-to-core conversion, including newtype construction; (d) authoritative core semantic/cross-field validation and stable error classification; (e) host-derived trusted context and exact Policy authorization immediately before a protected side effect; (f) one injected effect with explicit idempotency, deadline/cancellation, and evidence rules when consequential; and (g) allowlisted bounded response projection before transport write. Caller inputs SHALL NOT establish trusted identity, Policy decisions, grants, ceilings, or host paths.
8. The Rust-native Pydantic-equivalent SHALL remain layered: exact-pinned `serde` derives and `schemars` schemas at transport/config DTO boundaries, Rust enums and fallible newtype constructors for structural validity, and explicit core validation for semantic/cross-field/state/policy invariants. Deserialization/schema success SHALL NOT be considered domain validation or authorization. No `validator`, `garde`, ORM validation layer, or runtime-schema validator is added without a separate concrete adapter-bound gap and dependency decision.
9. All object DTOs at an external boundary SHALL use closed serde schemas (`deny_unknown_fields` unless an explicitly documented extension map is required), deliberate enum tagging/renaming, raw and semantic ceilings, and private conversion. External responses SHALL use separate safe projection DTOs, cap serialized output before write, and omit internal causes, secrets, paths, trusted context, and raw Policy artifacts unless a specification explicitly authorizes an evidence projection.
10. Mandatory status-only `<brick>` package trees are `Cargo.toml`, `src/lib.rs`, `src/model.rs`, `src/validation.rs`, `src/error.rs`, `src/port.rs`, `src/service.rs`, and `tests/public_contract.rs`. Each placeholder identifies the package metadata status, contains documentation/comments only, and compiles with no dependencies or exported semantic API. Once a responsibility becomes real, its named module and corresponding contract test replace the placeholder; no path is renamed. The same vocabulary keys the adapter modules of an implemented brick, so a path predicts its contents: `src/lib.rs` holds crate documentation, feature-gated `mod` declarations, and re-exports; `src/{model,validation,error,port,service}.rs` hold the core; `src/mcp.rs` or `src/mcp/{mod,dto,convert,service}.rs` holds the MCP surface; `src/memory.rs` and `src/fs.rs` hold local adapters. A `role = "server"` package under `projects/` uses `src/{main.rs,config.rs,composition.rs}` plus `tests/stdio_smoke.rs`.
11. The standard SHALL guide a behavior-preserving migration of existing crates. First, approve and inventory package roles/owned ports/public APIs. Next, move MCP stdio lifecycle from Agent, Project, Workflow, and Evaluation MCP libraries into thin server binaries while retaining bounded DTO behavior. Then normalize layout, closed schemas, newtypes, limits, error projections, and metadata; extract shared contracts only after two consumers prove a stable narrow need. Vendor, durable, remote, async, and mesh adapters remain separately specified work. Project Blueprint V1 SHALL NOT stamp these package families; a dedicated, separately approved successor is required.

## Non-goals

No portfolio-wide framework selection; mass import of provider/storage/runtime dependencies; automatic crate generation; change to existing core behavior during standard publication; generic dynamic discovery; an MCP aggregation runtime; or a claim that all portfolio entries are production-ready once scaffolded.
