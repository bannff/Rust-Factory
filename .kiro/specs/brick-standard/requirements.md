# Canonical Brick Standard

Define the Rust-native taxonomy and scaffold contract for the full Rust Factory portfolio before creating or refactoring further brick families. This standard is a reusable architecture contract, not a generic runtime or a line-for-line port of Python Factory/Polylith.

1. Every portfolio item SHALL be classified as exactly one of: a capability family, adapter infrastructure, composition base, or optional domain pack. Only a capability family may own a `<brick>-core`; shared infrastructure such as `mcp-transport` is an adapter, and MCP/API/worker/edge processes are composition-base binaries, never cores. The portfolio table is the family-level registry and states each approved mature shape.
2. Every approved capability-family scaffold SHALL use the mandatory, agent-maintainable core package tree from requirement 10, even before its semantic contract is implemented. A status-only scaffold is a narrow exception to core eligibility: it contains only compile-safe status documentation and private placeholder modules/tests, has zero non-stdlib dependencies, exposes no public semantic API, and claims no behavior or guarantees. It SHALL be replaced by a specified or implemented core contract before any adapter role is instantiated.
3. A specified or implemented `<brick>-core` is permitted only when the family owns stable typed models, deterministic rules, error taxonomy, and at least one consumed effect port. It is a library and owns versioned models/commands/results/events, validated newtypes, semantic validation, public-safe error categories, state invariants, and consumed port traits. It SHALL NOT depend on adapters, transports, `rmcp`, Tokio runtime/I/O, provider/storage/network/filesystem frameworks, or concrete adapter types.
4. Every Cargo package under this standard SHALL declare an authoritative machine-readable record in `[package.metadata.rust-factory]`: `family`, `role`, and closed `status` (`scaffolded`, `specified`, `implemented`, `migration-pending`, or `deprecated`). Only implemented adapters may declare guarantee metadata. Crate-level documentation SHALL mirror this data for human readers. Status is not a public Rust API and is never inferred from version or dependencies; the first rollout batch SHALL include deterministic metadata/layout validation so the workspace, package metadata, and Vision tracker cannot drift.
5. Optional adapter roles have one explicit eligibility rule: `<brick>-memory` is instantiated only after a concrete core-owned stateful port and truthful process-local semantics exist; `<brick>-<vendor>` only to implement one existing core port; `<brick>-mcp` only after a bounded authoring/operational surface is specified; `<brick>-server` only after a composition topology is specified; `<brick>-mesh` only after an approved process-boundary/mesh specification; and `<brick>-test-support` only after two consumers need shared fixtures/builders. No generic `factory-core`, prelude, utility, backend, storage, or validation umbrella crate may be introduced.
6. `<brick>-server` SHALL be a binary-only composition root. It owns runtime lifecycle, transport binding, configuration sources, host-derived trusted context, Policy resolver construction, concrete adapter selection/injection, logging initialization, and orderly shutdown. `*-mcp` crates SHALL expose transport-agnostic service/handler construction only; they SHALL NOT read `stdin`, write `stdout`, call `serve_stdio`, construct `BoundedStdioTransport`, or choose Tokio process lifecycle.
7. Each external operation SHALL follow this bounded sequence: (a) adapter transport framing and byte/item/depth limits; (b) strict boundary DTO deserialization and generated discovery schema; (c) private DTO-to-core conversion, including newtype construction; (d) authoritative core semantic/cross-field validation and stable error classification; (e) host-derived trusted context and exact Policy authorization immediately before a protected side effect; (f) one injected effect with explicit idempotency, deadline/cancellation, and evidence rules when consequential; and (g) allowlisted bounded response projection before transport write. Caller inputs SHALL NOT establish trusted identity, Policy decisions, grants, ceilings, or host paths.
8. The Rust-native Pydantic-equivalent SHALL remain layered: exact-pinned `serde` derives and `schemars` schemas at transport/config DTO boundaries, Rust enums and fallible newtype constructors for structural validity, and explicit core validation for semantic/cross-field/state/policy invariants. Deserialization/schema success SHALL NOT be considered domain validation or authorization. No `validator`, `garde`, ORM validation layer, or runtime-schema validator is added without a separate concrete adapter-bound gap and dependency decision.
9. All object DTOs at an external boundary SHALL use closed serde schemas (`deny_unknown_fields` unless an explicitly documented extension map is required), deliberate enum tagging/renaming, raw and semantic ceilings, and private conversion. External responses SHALL use separate safe projection DTOs, cap serialized output before write, and omit internal causes, secrets, paths, trusted context, and raw Policy artifacts unless a specification explicitly authorizes an evidence projection.
10. Mandatory status-only `<brick>-core` package trees are `Cargo.toml`, `src/lib.rs`, `src/model.rs`, `src/validation.rs`, `src/error.rs`, `src/port.rs`, `src/service.rs`, and `tests/public_contract.rs`. Each placeholder identifies the package metadata status, contains documentation/comments only, and compiles with no dependencies or exported semantic API. Once a responsibility becomes real, its named module and corresponding contract test replace the placeholder; no path is renamed. Implemented adapters use their fixed role trees: memory `src/{lib.rs,adapter.rs}` plus `tests/adapter_contract.rs`; MCP `src/{lib.rs,dto.rs,convert.rs,service.rs}` plus `tests/mcp_contract.rs`; server `src/{main.rs,config.rs,composition.rs}` plus `tests/stdio_smoke.rs`.
11. The standard SHALL guide a behavior-preserving migration of existing crates. First, approve and inventory package roles/owned ports/public APIs. Next, move MCP stdio lifecycle from Agent, Project, Workflow, and Evaluation MCP libraries into thin server binaries while retaining bounded DTO behavior. Then normalize layout, closed schemas, newtypes, limits, error projections, and metadata; extract shared contracts only after two consumers prove a stable narrow need. Vendor, durable, remote, async, and mesh adapters remain separately specified work. Project Blueprint V1 SHALL NOT stamp these package families; a dedicated, separately approved successor is required.

## Non-goals

No portfolio-wide framework selection; mass import of provider/storage/runtime dependencies; automatic crate generation; change to existing core behavior during standard publication; generic dynamic discovery; an MCP aggregation runtime; or a claim that all portfolio entries are production-ready once scaffolded.
