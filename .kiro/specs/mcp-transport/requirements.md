# MCP Transport Extraction

GitHub issue: #4

Extract the bounded server-side MCP stdio framing contract into adapter-only `mcp-transport` infrastructure. It is a transport utility for the one unified project MCP server, not a Factory core, runtime registry, router, binary, or deployment framework. Issue #17 owns its first bounded production use.

1. `mcp-transport` SHALL be a root workspace member with exact-pinned transport dependencies. Bricks SHALL NOT depend on it: only a `role = "server"` composition root under `projects/` binds transport. No library may own stdio or process lifecycle.
2. It SHALL expose `BoundedStdioTransport<R, W>` for the rmcp server role and `MAX_MCP_STDIO_FRAME_BYTES = 64 * 1024`. On ingress this is the maximum newline-delimited JSON-RPC payload size; LF and an optional immediately preceding CR are framing delimiters and are excluded from the payload ceiling.
3. Ingress SHALL be bounded incrementally before JSON-RPC or typed `Parameters<T>` deserialization. The transport accepts exactly 64 KiB framed with LF or CRLF and rejects 64 KiB plus one, including a non-CR partial frame before any newline. The only partial state above the ceiling is exactly 64 KiB plus a trailing CR awaiting LF.
4. An over-limit or non-Serde framing error SHALL terminally close the transport without emitting a response or dispatching a queued successor frame. Syntax/EOF malformed JSON follows rmcp-compatible ignore behavior; well-formed data/shape errors may receive rmcp's generic invalid-request response. No behavior may reveal adapter internals. Valid partial input SHALL survive receive-future cancellation and re-poll without loss.
5. Before every write, `BoundedStdioTransport::send` SHALL serialize and measure the complete `TxJsonRpcMessage`, including the caller-controlled JSON-RPC request ID. It SHALL reject an envelope larger than 64 KiB before writing any bytes and SHALL NOT emit a partial frame. Sends remain serialized through the transport writer. Smaller brick-result or project-meta-tool limits provide headroom only; they SHALL NOT be described as proof of the complete wire bound. Contract tests SHALL include an exactly-at-limit envelope, an over-limit envelope, and a near-limit request ID plus result.
6. Every deployable project SHALL construct exactly one `BoundedStdioTransport` and exactly one unified MCP server/router. That router statically combines selected brick `HandlerContribution`s and separately typed `factory_*` project meta-tools. It SHALL NOT substitute rmcp's unbounded stdio transport, launch per-brick server processes, or discover handlers dynamically. Issues #6 and #39 own the first unified project composition and sample-project direction; this specification preserves transport safety rather than defining those capabilities.
7. Existing handler schemas, trusted-context/Policy gates, public error projections, and typed core contracts remain capability-owned. Every non-introspection tool or project meta-tool SHALL receive host-derived context and exact Policy authorization before effects or tenant-scoped reads. This extraction does not authorize privileged operations, caller-derived trust, remote clients, async core ports, or a shared runtime abstraction.

## Non-goals

No client-role transport; socket/HTTP transport; dynamic plugin loading; process configuration; binary startup; per-brick servers; remote inter-brick calls; policy forwarding; capability routing semantics; or changes to core dependency direction.
