# Rust Factory Delivery Workflow

Use this workflow for every non-trivial brick, public API change, adapter, concurrency change, or dependency decision. The goal is to apply focused expertise without creating a generic committee or duplicating investigation.

## Standard sequence

1. **Repository context — `context-gatherer`**
   Map existing crates, contracts, call sites, tests, specifications, and steering before design or implementation. Reuse prior context when the question is unchanged.

2. **Rust design gate — `rust-factory-sme`**
   Review the intended crate boundary, trait/adapter ownership, public API, Cargo dependencies, ownership/concurrency model, error taxonomy, resource bounds, and framework choice. Resolve all Blocker and Required findings before implementation.

3. **Implementation — `implementer`**
   Build the smallest vertical slice that proves the brick contract. Apply `rust-fundamentals`, `rust-architecture`, `rust-quality`, and `rust-async` skills. Core crates remain framework-free; adapters receive concrete dependencies through injection.

4. **Adversarial QA — `qa-tester`**
   Add or assess deterministic behavior tests, state-transition/race tests, limits, malformed input, tenant isolation, idempotency, and public-contract cases. Generated fixtures must pass their own quality gate when applicable.

5. **Security gate — `security-reviewer`**
   Review authorization/context derivation, capability boundaries, input/output ceilings, cancellation, filesystem/network confinement, idempotency, evidence handling, secret/path/error leakage, and unsafe side effects. Resolve Blocker and Required findings.

6. **Final API/architecture gate — `meta-architect` and `rust-factory-sme`**
   Confirm the final code remains faithful to the spec and Living Factory Vision, dependency direction is inward, lifecycle ownership is correct, and future adapters have a clean seam.

7. **Quality and documentation**
   Run `make check`. Update the applicable spec tasks, README/API documentation, and living steering only when implementation evidence changes the agreed design. Use `doc-writer` when user-facing or architectural documentation needs review.

## Decision rules

- **Framework-first:** Before adding a dependency, the Rust SME must identify the concrete gap and ensure the chosen crate is contained in an adapter.
- **Async-first for I/O-concurrency execution paths, sync-first everywhere else:** The agent/LLM/workflow execution path is I/O-concurrency-bound by design (many concurrent agents, each making concurrent provider calls, across many concurrently starting/stopping workflows). For that path — `agent`, `llm-gateway`, `workflow`, and future execution-layer work (agent-server, squad execution, any new `model-gateway`-shaped provider adapter) — default new public core traits and ports to `async`, using Tokio as the workspace's one async runtime. Keep the existing runtime-neutral shape: core traits stay executor-agnostic (they must compile and be testable without pulling in `tokio` as a core dependency, as `llm-gateway` and `workflow` already do), and an actual Tokio runtime is instantiated only by a composition root or transport adapter (as `mcp-transport` already does), never by a core crate.
  Do not force async onto bricks or modules with no I/O and no concurrency need. `policy`'s decision logic, `sandbox`'s core validation, and `observability`'s core telemetry model/validation gain nothing from async and stay synchronous; only a specific I/O adapter within such a brick (e.g. an OTEL span exporter) may need to bridge sync-to-async internally, and that bridging stays inside the adapter, not the core trait.
  This reverses the prior "start synchronous, add Tokio only for a demonstrated requirement" default specifically for the execution path; it does not require converting already-shipped synchronous ports outside that path, and it does not make async a default for bricks without an I/O-concurrency requirement.
- **Async-first is forward-looking, not retroactive, unless a dedicated migration issue says otherwise:** `llm-gateway`'s `LlmProvider` and `workflow`'s `AgentInvoker`/`WorkflowRunner` invocation path are already async (boxed-future ports, no `.await` conversion needed). `workflow`'s `WorkflowStore` persistence port and `observability`'s `TelemetrySink`/`SpanSink`/`MetricSink` ports are synchronous today and stay synchronous until each has its own dedicated migration issue with a demonstrated I/O-concurrency requirement — do not convert them as a side effect of this default. New execution-layer work (agent-server #6, squad execution #48, any future `AgentRuntime` or `WorkflowExecutor` port) adopts async from its first draft, through the Rust design gate, rather than starting sync and converting later.
- **Tokio is the standard runtime; core dyn-dispatched traits keep the boxed-future shape.** Tokio (pinned in root `Cargo.toml`) is the only async runtime this workspace adopts; do not introduce a second runtime (e.g. `async-std`, `smol`) for any brick. For a core trait that must support `dyn` dispatch across adapters (the existing pattern in `LlmProvider::generate` and `AgentInvoker::invoke`), keep returning a manually-desugared `Pin<Box<dyn Future<Output = T> + Send + 'a>>` rather than native `async fn` in the trait — RPITIT is not `dyn`-safe without this erasure, and this workspace already relies on trait objects (`Box<dyn LlmProvider>`, `Box<dyn AgentInvoker>`). Native `async fn` in a trait is acceptable only where the trait is consumed solely through static generics (no `dyn` requirement) and object safety is not needed. Either way, the core trait itself stays executor-agnostic: no `tokio::spawn`, `tokio::time`, or `tokio::select!` inside a core crate's public API. A concrete Tokio runtime is instantiated once, in the composition root/adapter layer only.
- **Issue #62 (OTEL span-export adapter): `observability` core ports stay synchronous; the OTEL span adapter bridges internally.** `SpanSink::emit` (and `TelemetrySink::emit`, `MetricSink::emit`) in `crates/observability/src/port.rs` remain synchronous `fn` returning `Result<(), ObservabilityError>`. The core telemetry model has no I/O-concurrency need of its own — it is a bounded local record/validate call, matching the existing `OpenTelemetryLogsSink`/`OpenTelemetryMetricSink` adapters, both synchronous today. The OTEL span exporter is the one component with a genuine async requirement (the upstream OTEL SDK's span exporter is async); that adapter bridges sync-to-async internally — e.g. handing the validated span to a bounded channel drained by a dedicated Tokio task/runtime the adapter owns — without changing the `SpanSink` trait signature or requiring `observability`'s core to depend on `tokio`.
- **No false durability claims:** A local/in-memory adapter must describe its actual guarantees. Leases, recovery, cross-process cancellation, retries, and exactly-once effects require their own specified durable adapter.
- **Approval is a gate:** `APPROVE` is required before a brick's spec is marked stable. Tests passing alone are not evidence that architecture or security requirements are met.
- **Scale down for trivial edits:** Documentation-only or mechanical renames may use context → implementation → `make check`; preserve the full gates for behavior, public API, dependencies, and safety changes.
- **Validate `make check` against CI's actual toolchain, not just the local default.** A local `stable` toolchain and CI's pinned toolchain can disagree on which Clippy lints are active (a lint added in a newer Clippy release fires in CI and not locally, or vice versa). Passing `make check` locally is not sufficient evidence that a PR's `quality` CI check will pass. Before pushing, or when CI fails a check that passed locally, run `rustup toolchain list` to see what's already installed, and if CI's exact version is available locally, verify with it directly (e.g. `cargo +<version> clippy --workspace --all-targets --all-features -- -D warnings`) rather than iterating blind against CI. If CI's version isn't installed locally, install it (`rustup toolchain install <version>`) before retrying. Do not treat a CI-only failure as a reason to weaken a lint or skip local verification going forward — closing the toolchain gap once prevents the same class of failure recurring on every subsequent PR.
- **A design gate can be blocked mid-implementation, not just before it.** If implementation surfaces a genuine conflict with an existing spec or a real API-shape mismatch (e.g. a chosen trait/dependency cannot actually satisfy the stated contract), stop and route it back through the design gate rather than coding around it or silently narrowing scope. Update the spec to match the corrected decision before implementation proceeds, and open a tracked follow-up issue for any descoped work rather than dropping it silently.
